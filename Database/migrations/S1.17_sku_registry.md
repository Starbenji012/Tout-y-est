# S1.17 — Références SKU permanentes

Format automatique : `TYE-P000001`, puis `TYE-P1000000` au-delà de six chiffres.
Le compteur est global par variante, indépendant des IDs et des numéros de commande.
Les anciennes références et les snapshots ne sont jamais renommés.

## Application locale

1. Exécuter `php Tests/Unit/SkuAllocationTest.php` : migration et scénarios en base jetable.
2. Exécuter `php Database/migrations/migrate-sku.php --local-backup-and-migrate`.
   Cette commande n'accepte que la base locale `tout_y_est`, vérifie le schéma et les
   ambiguïtés, suspend les écritures catalogue avec le verrou commun, sauvegarde la base
   complète dans `Storage/backups` (ignoré par Git), restaure la sauvegarde dans une base
   jetable et compare les données. Elle applique ensuite la migration, importe les SKU
   du catalogue ET des commandes et vérifie l'identité des anciennes tables.
3. Conserver la sauvegarde et son manifeste de vérification hors publication.

Ne pas exécuter uniquement le fichier SQL sur une base existante : `SkuMigration::apply`
effectue aussi les contrôles et l'import. Le SQL est inclus dans le schéma des bases neuves.
Les services PHP chargés doivent être ceux de cette version pendant la migration.
Un ancien processus ou un accès SQL externe qui contourne les services doit être arrêté.
Les sources `variante_produit` et `ligne_commande` sont également verrouillées en lecture
pendant l'import ; une commande concurrente peut donc attendre brièvement.
La migration est rejouable et ne remet jamais le compteur à zéro. MariaDB 10.4 est la
cible vérifiée ; un autre serveur exige une validation préalable.

## Réservations et idempotence

`SkuService` utilise une connexion d'allocation distincte, vers la même base et le même
serveur. Une transaction courte verrouille la ligne de `sku_sequence`, choisit une
référence libre et l'inscrit dans `sku_attribution`, puis commit avant l'écriture métier.
Les SKU manuels suivent le même registre et la validation existante. Une saisie manuelle
peut réserver un futur numéro automatique : le générateur sautera ce numéro.

Une ligne `origine=operation` du registre (sans SKU) mémorise l'empreinte de la demande
et son résultat. La clé est liée à l'administrateur et au parcours ; les formulaires
transmettent `sku_request` (32 caractères hexadécimaux). Les appels serveur peuvent passer
la même clé optionnelle pour rejouer une création. Sans clé, chaque appel est une nouvelle
intention. Une même clé avec une saisie différente est refusée (409).

Les références du lot sont réservées avec des clés déterministes dérivées de l'opération.
Le résultat et le rattachement des variantes sont commit ensemble dans la transaction
métier. Après rollback, la réservation persiste ; une reprise identique la retrouve.
Un résultat déjà commit est retourné sans recréer produit, options ou variantes.
Les trous sont normaux. Aucun SKU abandonné ou remplacé n'est libéré, même manuellement.

Les triggers interdisent DELETE du registre, changement de son identité, modification
d'un propriétaire déjà lié ou d'un résultat acquis, et recul/suppression du compteur.
Ne jamais utiliser TRUNCATE, DROP, réinitialisation ou restauration d'une ancienne copie
du registre sur un système actif. Ces commandes administratives peuvent contourner les
protections DML. Restaurer ensemble catalogue, registre et compteur ; après une perte
de sauvegarde, réconcilier aussi toute attribution postérieure avant reprise des ventes.

## Limites

- Les écritures administratives catalogue sont sérialisées par un verrou commun de
  maintenance. Les lectures restent disponibles ; attente maximale habituelle : 30 s.
- Les références anciennes disparues de toutes les données/archives sont irrécupérables.
- Les SKU restent `VARCHAR(100)` ; le compteur est `BIGINT UNSIGNED`, manipulé comme chaîne
  décimale en PHP. Son épuisement est refusé explicitement, sans retour à zéro.
- Pas de rollback destructif fourni : revenir à l'ancien générateur ferait perdre la
  garantie de non-réutilisation des références manuelles. Conserver les deux tables.
- Aucun changement aux commandes, paniers, règles de stock, seeds, ni phases 4C-2/5.
