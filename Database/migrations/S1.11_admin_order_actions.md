# S1.11 — Actions Admin commandes

Ajoute uniquement `journal_commande`. Aucun changement des données métier existantes.
Sélectionner explicitement la base cible avant d'exécuter le SQL ; sauvegarde habituelle
recommandée avant tout DDL. Ne pas rejouer schema.sql sur une base existante.

La création est rejouable avec IF NOT EXISTS ; elle ne répare pas une table préexistante
de définition différente. Les tests vérifient la migration sur une base éphémère.
Cette migration n'est pas appliquée automatiquement par l'application.

Une action donnée ne peut survenir qu'une fois par commande dans le parcours V1
sans retour arrière. L'unicité commande/action protège le journal, en plus du verrou
de commande. L'acteur, les états avant/après, le paiement et le contexte financier
ou motif sont enregistrés par le serveur dans la même transaction que l'action.
Échec du journal = rollback, y compris de la restitution du stock.

Les trois FK empêchent la disparition des références historiques. Aucun endpoint
de modification ou suppression du journal n'est exposé. Ne pas supprimer ce journal
pour annuler une action : les remboursements/retours restent hors V1.

L'encaissement utilise exclusivement les montants et devises historiques serveur :
devise_paiement, sinon devise_reglement déjà renseignée, sinon devise de référence USD.
Une incohérence entre snapshots est refusée. Aucun choix de devise ou montant n'est
accepté du navigateur. Un règlement CDF est calculé au taux figé, en francs entiers
selon MoneyService, puis stocké en DECIMAL sans division par 100.
