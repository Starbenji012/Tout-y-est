# S1.16 — Options et variantes, Phase 4A

Migration additive MariaDB 10.4.32, à appliquer manuellement après sauvegarde,
précontrôle de la cible/structure et hors trafic. DDL à commit implicite : une
transaction PHP ne rend pas un déploiement DDL globalement atomique. Le rejeu
est prévu pour la même structure ; un objet homonyme divergent doit faire
l'objet d'un diagnostic, pas d'une réparation silencieuse.

Cette phase ne déploie pas la migration sur `tout_y_est`. Aucun nouveau service,
écran ou comportement public n'est introduit. Les tables caractéristiques et
legacy restent séparées et intactes. Prix, devise, stock, SKU, description et
IDs restent sur les mêmes variantes ; aucune option n'est inventée pour elles.

## Garanties SQL

- `option_produit` : produit propriétaire, nom et position 1..3 unique par
  produit. Trois positions et UNIQUE garantissent au maximum trois options.
- `valeur_option_produit` : option propriétaire, libellé et ordre non négatif
  (`SMALLINT` et CHECK >= 0). Un type signé évite le rabattement silencieux de
  -1 vers 0 par un mode SQL non strict avant validation. Les ex aequo sont
  permis, départagés par `id_valeur`.
- Les noms/libellés normalisés générés utilisent `LOWER(TRIM(...))` et la
  collation explicite `utf8mb4_unicode_ci` : casse, espaces de bord ordinaires
  et différences d'accents ne créent pas de doublons dans un même propriétaire.
  La normalisation complète Unicode/espaces intérieurs relève du futur service.
- `variante_valeur_option` : une seule valeur par option/variante (PK), et
  trois FK composites contrôlent variante-produit, option-produit et
  valeur-option. Les UNIQUE composites parents sont explicites. RESTRICT
  évite une suppression/réaffectation qui ferait disparaître une définition.
- `uq_variante_combinaison` garantit l'unicité par produit d'une clé non NULL.
  La clé ASCII distingue précisément les identifiants, pas les libellés.

## Clé canonique et transition

`cle_combinaison VARCHAR(160) ASCII ascii_bin NULL DEFAULT NULL` :

- `NULL` : non classifiée dans le nouveau moteur. Toutes les variantes
  existantes conservent cette valeur, sans collision même si un ancien produit
  possède plusieurs variantes sans options. Le code 3A reste compatible.
- `simple` : future variante simple explicitement gérée par 4B ; UNIQUE interdit
  deux variantes classifiées `simple` sur un même produit.
- `id_option:id_valeur|id_option:id_valeur|...` : de une à trois paires, IDs
  décimaux positifs sans zéros initiaux, triés par ID d'option croissant.
  Exemple `12:45|19:61`. VARCHAR(160) couvre trois paires de BIGINT UNSIGNED.
  CHECK valide la forme et l'ordre numérique strict des options. Renommer ou
  réordonner les libellés/options ne change donc pas l'identité.

**Limite explicite :** UNIQUE ne couvre pas les NULL, par compatibilité
transitoire. SQL ne démontre pas que la chaîne correspond aux lignes de
l'association, ni que toutes les options du produit sont renseignées. Un client
SQL direct pourrait donc construire une identité incohérente avec ses liens.
Le service 4B devra calculer et exiger la clé, valider l'ensemble et écrire
clé + associations dans une seule transaction, sans faire confiance au client.
Pas de prétendue garantie interlignes apportée par un simple CHECK.

## Maximum 100 : Phase 4B

Pas de trigger ni de colonne de compteur artificielle en 4A. SQL ne borne pas
le nombre de variantes à 100. 4B devra verrouiller le produit et compter toutes
ses variantes (actives et inactives) avant chaque création ou lot ; refuser si
le résultat dépasse 100. Tous les chemins d'écriture devront suivre ce verrou.
Les combinaisons seront sélectionnées explicitement : pas de matérialisation
automatique du produit cartésien. Tests de concurrence obligatoires en 4B.

Les IDs d'anciennes variantes référencées par panier/commande ne seront jamais
recréés ni réaffectés à une autre combinaison. Les descriptions historiques
restent des snapshots, pas des jointures sur les nouveaux libellés.

## Rollback

`S1.16_product_options_rollback.sql` exige une S1.16 complète et inutilisée :
trois nouvelles tables vides et toutes les clés NULL. Sinon le précontrôle
échoue avant toute suppression durable. Aucun effacement automatique des
options ou déclassification des variantes n'est effectué. Après utilisation
de 4B, exporter/résoudre les données avant d'envisager un rollback.

Le rollback retire uniquement les objets ajoutés et conserve l'index support
de la FK produit historique. Les anciennes variantes et leurs relations ne
sont pas supprimées. Le rollback n'est pas un outil de réparation d'une
installation partielle ni un script à rejouer sur une base non migrée.
