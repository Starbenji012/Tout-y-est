# S1.14 — Préaffectation exclusive des livreurs

À appliquer manuellement après sauvegarde et contrôle local. Ce lot ne l'applique pas à tout_y_est.

Précontrôle : rechercher les livreurs affectés à plusieurs livraisons en préparation/en livraison. Si de tels doublons existent, STOP : aucune correction automatique des anciennes livraisons. La création de l'index échouera sans supprimer de données.

Deux colonnes calculées n'introduisent aucun état métier persistant :
- livraison.id_livreur_engage impose une seule affectation active par livreur (préparation ou livraison) ;
- journal_commande.action_unique reste NULL pour assign, et conserve l'action pour les cinq transitions uniques.

Les nouveaux index sont créés avant retrait de l'ancienne unicité. Le CHECK autorise assign. Rejouable sous MariaDB 10.4 ; aucune référence, aucun prix, paiement, stock ou snapshot existant n'est réécrit. DDL non transactionnel : contrôler les éventuels changements partiels après un échec avant tout rejeu. Pas de rollback destructif automatique : des réaffectations multiples ne pourraient pas rentrer dans l'ancienne unicité.

Disponibilité administrative : actif/inactif, sans date inventée. État affiché dérivé des livraisons : Disponible, Affecté — départ en attente, En course. En cas d'inactivité pendant une affectation/course, l'occupation reste visible avec l'interdiction des nouvelles affectations. Le départ est refusé pour un livreur administrativement inactif ; réaffectation explicite possible avant départ.

Préparer = passage existant en_preparation, sans départ automatique. Affectation des commandes préparées sans livreur par date_preparation, puis date_commande et ID ; livreurs libres par ID croissant. Une affectation existante n'est jamais remplacée automatiquement. Une réaffectation manuelle exige l'ancien ID affiché et une confirmation. Chaque changement réel écrit assign (ancien/nouveau nom et ID, origine automatique/administrateur, date et Admin déclencheur).

Les mutations verrouillent tous les livreurs par ID avant commande/paiement/livraison. La contrainte unique constitue une seconde défense. La V1 sérialise volontairement cette courte file ; aucun débit à grande échelle n'est promis. Une livraison terminée ou annulée libère l'occupation, puis la même transaction affecte la plus ancienne commande éligible. L'activation administrative déclenche également cette file. Aucun traitement au GET, aucun scheduler, aucune réécriture au renommage.

Les anciennes livraisons sans ID ne sont pas rapprochées par nom. Après déploiement, une file préexistante est traitée lors de la prochaine préparation, activation, livraison, annulation ou affectation manuelle autorisée, jamais au chargement d'une page.
