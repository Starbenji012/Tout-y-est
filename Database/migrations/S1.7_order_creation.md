# S1.7 — Commande et réservation

Migration additive : clé SHA-256 d'idempotence unique par utilisateur, échéance de réservation et date de restitution. Les anciennes lignes gardent NULL. Sauvegarder avant application ; le DDL MySQL/MariaDB n'est pas transactionnel. Ne pas relancer la migration si ses colonnes existent déjà.

`OrderService` possède la transaction. Le verrou du compte sérialise les créations d'un même utilisateur ; panier et variantes sont relus sans plafonner ni retirer de ligne. La clé brute aléatoire est émise et contrôlée en session, seule son empreinte est persistée. Une nouvelle page Checkout émet une nouvelle clé ; les dix dernières restent acceptées pour les retries.

Les prix USD sont recalculés en cents. Le taux serveur est figé sur commande ; l'étape 2 utilise exclusivement ce snapshot pour le CDF. La devise choisie et le montant de règlement restent NULL jusqu'au futur lot Paiement. Aucun paiement n'est créé.

La commande `en_attente_paiement` réserve le stock pendant trente minutes, selon l'heure BDD. Le paiement futur ne doit pas décrémenter à nouveau. Annulation/expiration : verrou commande, restitution et horodatage dans la même transaction. Une seconde restitution est impossible via ce service. Le panier n'est pas vidé.

`expireReservations(limit)` est le point d'entrée interne pour un futur cron. La consultation d'une commande expirée libère aussi sa réservation. Sans appel planifié, les réservations abandonnées sans consultation restent immobilisées : configurer un appel régulier avant production. Aucun scheduler ni endpoint public d'annulation libre n'est ajouté.

Tests de concurrence dans une base éphémère `tout_y_est_order_test_<aléatoire>`, supprimée à la fin. Aucune commande ni modification du stock du catalogue local réel n'est nécessaire pour les tests automatiques.
